# Выпуск и совместимый откат аффирмаций

Разработка ведётся только в feature/affirmation-history. Выпуск и откат
работающего бота требуют отдельного разрешения владельца.

## Перед выпуском

1. Проверить успешный GitHub Actions на точном выпускаемом коммите.
2. Зафиксировать текущий коммит main и действующий deploy Render.
3. Из checkout с полной историей подготовить прежний код:
   python scripts/prepare_rollback.py --output ../affirmation-compatible-rollback
4. Сохранить подготовленный каталог в отдельной ветке отката перед выпуском.
   Его основа — d1a4860814cb1492adfda0174bfffef6a856b141, с поддержкой
   статусов active, cancelled, superseded и существующего payload/data.
5. Получив доступ к базе в доверенной среде с DATABASE_URL, выполнить:
   python scripts/backup_affirmations.py --output /защищённый-путь/history-before.json
   python scripts/backup_affirmations.py --verify /защищённый-путь/history-before.json
   Подключаться к primary действующей базы, проверить принадлежность строки id=1.
6. Сохранить проверенный файл в постоянное закрытое хранилище вне публичного GitHub.
   Копия содержит личные тексты. Файл в scratch или на диске Render временный.
7. После разрешения объединить проверенный коммит с main и дождаться Live в Render.
   Проверить /health и журналы. Изменений схемы базы и cron-job.org не требуется.
8. Проверку с реальным сообщением Telegram выполнять только с отдельного согласия.

## Если нужен откат

1. Сообщить владельцу о проблеме, согласовать откат.
2. Сделать дополнительный read-only экспорт актуальной истории, если база доступна.
3. Выпустить подготовленную совместимую предыдущую версию кода.
   Она использует текущую PostgreSQL. Восстановление старого дампа не выполняется.
4. Проверить Live, /health, журналы и выбор аффирмации без внепланового Telegram.
5. Убедиться, что основной список аффирмаций, архивные версии и остальные поля
   сохранились. Новое управление историей будет доступно после повторного выпуска
   исправленной новой версии. Прежний /affirm после отката имеет прежнее поведение.

## Что проверяют тесты

Изолированная PostgreSQL получает задачи, напоминания, дневник, личную заметку,
профиль Ба-цзы и историю аффирмаций. Затем выполняются:
экспорт до изменения; добавление записи; перенос даты; отмена другой записи;
экспорт после изменения; подготовка и загрузка прежнего приложения с совместимым
выбором; обработка /today прежним приложением.

Проверяются совпадение всей строки до и после отката, контрольные суммы обеих
копий, выбор текста на нескольких датах, сохранность архивов и профильных колонок.
Новые и отменённые записи сохраняются, а отменённые тексты не выбираются утром.

## Ограничения проверки

На этапе разработки используются тестовые данные, без подключения к рабочей Neon.
Возможность read-only экспорта подтверждена на тестовой PostgreSQL. Доступность
конкретного рабочего подключения, права пользователя и сохранение реального
файла нужно подтвердить перед выпуском.

## Дополнительная проверка существующей схемы перед выпуском

В рабочей Neon подтверждена колонка payload. Старый исходный код использовал
data. В тестовой ветке оба варианта поддерживаются через state_storage.py.
Он не добавляет колонок, не переносит данные и не меняет version.
Совместимый откат включает этот же слой и учитывает cancelled/superseded.

Перед выпуском выполнить только чтение scripts/check_state_schema.sql
в primary / neondb. Сопоставить форму payload с поддерживаемым состоянием.
Наличие одной колонки ещё не подтверждает внутреннюю структуру её JSON.
Если она другая, сначала адаптировать код на тестовых обезличенных данных,
повторить тесты. Автоматически обнулять или мигрировать рабочий payload нельзя.

Ранее созданная пользователем копия affirmations_history проверена вручную
22 ноября 2026: одна запись с 2026-11-16, декабрьской записи нет. При выпуске
проверить актуальность копии, если после этой даты история редактировалась.
